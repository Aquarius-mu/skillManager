# 审查方法论（所有专项 agent 共用）

这份文件定义**问题成立与否的判据**。六个专项 agent 关注面不同，但裁决规则完全相同。
编排器会把本文件内容注入每个 subagent 的 prompt。

---

## 一、行号锚定（第一步，先过这关）

你会拿到一份 `<line_ranges>`：`{文件: [[新文件起始行, 新文件结束行], ...]}`，由脚本从 diff 的 `@@` 头解析得出。

**每条 finding 的行号必须落在 `line_ranges` 覆盖的区间内。**

- 行号超出区间 → 这个问题不属于本次改动 → **直接丢弃**，不进入后续任何环节
- 不要报 diff 范围之外的存量问题
- 引用行号时，用 diff 中标注的**新文件行号**

---

## 二、"先证明安全，再证明有问题"

对每个疑点，**固定按这个顺序走**：

1. 先找当前路径上**已有的保护**：guard、契约、初始化、生命周期、上层框架保证、同类安全模式
2. 只有安全证明**失败**，才继续构造失败路径

**找不到失败路径的候选，不输出。**

这条决定了你不该怎么做：不要先假设"这里可能有问题"，然后去找支持它的理由。要找的是**推翻它**的理由，推不翻才留下。

---

## 三、候选卡片（写不满 4 行 = 证据不够，不得上报）

每个候选问题在上报前，压缩成一张卡片：

| 字段 | 含义 |
|---|---|
| `risk_point` | 具体哪一行、哪个访问或哪条状态变更有风险 |
| `claim` | 你声称会发生什么 |
| `existing_guards_checked` | 你检查过哪些现有保护、契约、初始化 |
| `failure_path` | 它**如何真实失败**——写不出具体输入/条件，直接过滤 |
| `patch_delta` | 本次改动如何引入或放大这个风险 |

**写不出 `failure_path` 的候选，一律不得进入最终报告。**

---

## 四、假设验证闭环

若候选问题依赖任何前提假设（"这个值可能为空"、"这个函数可能返回错误"、"这里可能有并发"）：

1. **显式列出**全部假设
2. **尝试证伪**：在当前可读代码范围内验证该假设是否成立
3. **矛盾即过滤**：若反证清单里已有条目直接否定某条假设 → **必须过滤**，不得保留

假设概率分级：

| 级别 | 判据 | 处理 |
|---|---|---|
| high | 有代码路径或输入可直接触发 | 正常上报 |
| medium | 需特定条件才触发 | 降一级（P0→P1，P1→P2） |
| low | 仅理论上可能，无代码证据 | **禁止上报** |
| none | 有代码证据证伪假设 | **必须过滤** |

**禁止的矛盾组合**（出现即过滤）：
- 假设"某函数可能抛异常" + 反证已确认"该函数无显式抛出 / 无异常路径"
- 假设"某值可能越界/为空/非法" + 反证已确认"存在明确 guard / 前置检查 / 初始化保证"

**反证预算**：每个候选最多再读 2 个额外文件，每个文件最多取与 claim 直接相关的 80 行。一旦某次读取已能证明安全，立即停止，不再扩展。

---

## 五、同类代码搜索（高误报类别强制）

以下类别**必须先在项目内搜索同类写法**，再决定报不报：

- 并发、线程安全、数据竞争
- 全局实例 / 单例 / 全局静态
- 多线程初始化、lazy init、双重检查锁
- 异步任务共享状态、线程池 / 协程 / 任务派发
- 主循环 / 框架回调（`loop` / `Tick` / `Update` / `OnLoop`）中的同步阻塞
- 基类 / 共享初始化方法中新增字段赋值，与子类 override 的赋值冲突
- 空指针 / 越界 / 资源释放类（搜索同 API 的调用点与 guard 写法）

**搜索顺序**：当前文件同目录 → 模块父目录 → 配对文件 → 全仓同类文件（每个候选最多采样 3 个文件，每个最多读 120 行）。
**停止条件**：前 1~2 个样本已形成稳定模式即可停止。

**裁决规则**：

| 搜索结果 | 处理 |
|---|---|
| 仓库内多个同类实现模式一致，本次只是沿用 | **过滤**，不输出 |
| 仓库有同类实现，但**本次相比同类新增了风险** | 保留，并写明"仓库既有模式 + 本次新增风险" |
| 仓库同类实现通常带保护，**本次缺少**该保护 | 保留 |
| 搜索结果分裂严重或证据不足 | **不得直接豁免**，最多降级 |
| 搜不到同类实现 | 不构成豁免依据，按常规证据链继续判断 |

**"新增风险"的定义**（满足任一）：
- 新增共享可变状态
- 移除或削弱锁、原子、线程边界、生命周期保护
- 扩大全局实例/单例的访问面、写入面或逃逸范围
- 新增跨线程、跨协程或异步访问路径
- 改变初始化/销毁时序，导致并发窗口变化
- 相比仓库同类写法缺少关键保护步骤
- 引入与仓库主流实现不一致的新分支或新模式
- 主循环回调中引入同步阻塞，而同目录同类回调均为立即返回模式

**反例警戒**：不得因为"邻文件也这么写"就放过——先确认那是不是同一个场景。抄先例抄错场景是真实踩过的坑。

## 六、证据强度 `evidence_strength`（决定能不能报高优先级）

| 强度 | 判据 | 允许的最高优先级 |
|---|---|---|
| `strong` | diff 中可直接看到触发路径，无需假设 | P0 / P1 |
| `medium` | 需要 ≤2 步推断，且假设已验证成立 | P1 / P2 |
| `weak` | 推断链 >2 步，或依赖未完全验证的假设 | **只能 P3，且影响分 ≤ 4** |

`assumptions` 非空且未经验证，或反证清单已部分否定假设 → 强度自动降为 `weak`。

---

## 七、严重度分级与强制降级

| 级别 | 含义 |
|---|---|
| **P0** | 数据丢失 / 崩溃 / 可刷取大奖 / 消息契约破坏（客户端卡死）/ 越权 |
| **P1** | 明确的功能错误、漏发、状态不同步、线上可复现的错误行为 |
| **P2** | 影响局部、有变通手段、或在极端条件下才触发 |
| **P3** | 低影响、可维护性问题 |

**强制降级约束**（必须遵守，不得报更高）：

1. **纯注释/文档错误**：注释与实现不符但无任何运行时副作用 → **最高 P3**
2. **测试/调试专用路径**：触发路径仅在 `bXxx_Debug` / `bXxx_Test` / 非线上宏块内可达 → **最高 P3**，且描述里必须注明"仅在测试/调试构建下触发"
3. **纯命名或裸数字违规**：仅违反命名约定或用了裸数字而项目已有等价枚举，**且不存在任何运行时逻辑 bug** → **强制 P3，不得报 P2**

**安全类硬性下限**：外部可触达的安全漏洞（客户端传参可刷、越权）一律 P0 或 P1。

## 八、输出契约（缺一即丢弃）

每条 finding 必须齐备六项：

1. **位置**：`文件:行号`，行号落在 `line_ranges` 内
2. **原文**：违规代码逐字引用（1~3 行）
3. **失败链条**：`当 <具体输入/状态> 时，会发生 <错误现象>，因为 <原因>`
4. **依据**：规范条文 / 需求文档出处 / 互逆函数实现 / 同类代码搜索结果
5. **置信度**：0–100（这条是不是真的）
6. **严重度**：P0 / P1 / P2 / P3

补充要求：
- **标题**：2~10 个字，说清是什么问题。**禁止**用 `代码问题`、`风险问题`、`实现问题`、`潜在问题` 这类空话
- **推荐分类词**：`空指针`、`越界访问`、`迭代器失效`、`资源泄漏`、`逻辑问题`、`边界问题`、`状态问题`、`并发问题`、`性能问题`、`安全问题`、`规则违规`、`数据不一致`、`消息契约`
- **问题代码块**：不少于 8 行（不足 8 行时按实际行数，禁止伪造），必须含至少一行变更行
- 一个 finding 只表达一个可独立修复的问题

置信度 < 75 或严重度 P2/P3 的写入「低置信度备选」，不混进主报告。

---

## 九、绝不报告

- 运行时不可能触发的边界（游戏数值有配置上限约束）
- 框架 / 调用约定已保证的前置条件
- diff 范围外的存量代码
- 纯格式、空行、缩进、linter 能处理的内容
- 无具体触发路径的猜测
- 无具体函数名对应的"建议复用"泛化建议
- 凑数的 finding
