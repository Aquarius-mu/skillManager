# 技术代码场景画板指南（Tech / Code Board Guide）

> 这是 beautiful-feishu-whiteboard 的**技术代码向定制层**。35 种配色风格与画板硬规则都不变（见
> [`CATALOG.md`](CATALOG.md) 与 [`RULES.md`](RULES.md)），这份指南告诉 agent 一件事：**游戏服务端 / 客户端
> 开发团队最常要画的图，该用什么布局形态、配哪个风格、注意哪些实现层面的坑。**
>
> 重心在「技术 / 代码实现」：代码架构、模块 / 类关系、调用链、协议消息结构、数据结构与存储、
> 状态机、算法控制流。策划 / 运营向的场景（玩法、数值、活动、时间线）降为次要，见第三节。

## 二、技术 / 代码场景详解

每个场景给三样东西：**布局建议**、**风格理由**、**实现层面的注意点**。

### 1. 代码模块 / 架构

- **布局**：分层 + 依赖。模块用圆角矩形（模块名 + 职责一行注释），层与层、模块与模块之间用
  直角 `polyline` 表达依赖 / 调用。典型分层：接口层 / 逻辑层 / 数据层，或 接入 / 逻辑 / 存储 / 跨服。
- **风格**：首选 **Raw Grid**（系统原生、黑白结构、数字感，最像工程图）；备选 **Riso Brut**、
  **Lime Slab**。
- **注意**：模块名 / 类名 / 文件名（`GameServer`、`ConquestServer`、`Redis`）**保留英文原样**，
  中文只做并列注释。依赖方向要标清楚「谁依赖谁」，别把所有箭头画成双向。

### 2. 类关系（继承 / 组合 / 依赖）

- **布局**：UML 类图。一个类画成一个三格矩形（类名 / 成员变量 / 方法），类之间用箭头 + 关系文字连接。
- **风格**：首选 **Monochrome**（文字优先，最接近 UML）；备选 **Raw Grid**。
- **注意**：飞书画板**画不出 UML 的空心三角（继承）/ 实心菱形（组合）箭头**——`polygon` 会嵌入成
  图片，箭头只能用 `marker-end` 实心箭头。所以关系一律「普通箭头 + 文字标注」：继承写 `extends` /
  `继承`，组合写 `持有` / `has-a`，依赖写 `依赖` / `uses`。C++ 语境下注明基类 / 派生类、组合 vs
  聚合的区别（生命周期归属）。

### 3. 调用链 / 时序

- **布局**：泳道。每个服务 / 模块 / 对象一条竖线，横向箭头 = 调用或消息，箭头上标方法名 / 消息名。
- **风格**：首选 **Monochrome**；备选 **Raw Grid**、**Avocado Press**。
- **注意**：同步调用和异步回调要区分（实线 vs 虚线 `line`），返回用回箭头。跨服转发标 `Forward`、
  主动下推标 `Push`。一次完整链路（登录 / 战斗 / 采集）从头画到尾，别只画中间一段。

### 4. 协议消息结构

- **布局**：字段块 + 流向。一个消息画成一个字段块（字段名 : 类型 : tag 号），请求 / 响应之间用
  箭头连接，或用一块面板列出消息族。
- **风格**：首选 **Raw Grid**；备选 **Long Table**。
- **注意**：字段名、类型（`int32` / `string` / 自定义 `PlayerIDType`）、`tag` 号**全部保留原样**，
  这是能和 SDP / 代码对上的关键。`CS`（客户端→服务器）、`SC`（服务器→客户端）、`Push`（下推）、
  `Forward`（跨服）四类消息要分组标注。

### 5. 数据结构 / 内存布局

- **布局**：字段块 + 嵌套。一个 `struct` / `class` 画成一个矩形，内部列出字段（`字段名 : 类型`），
  数组标 `[N]`，嵌套 struct 用包含箭头或缩进表达。
- **风格**：首选 **Raw Grid**；备选 **Long Table**。
- **注意**：类型、数组维度、嵌套关系要准。稀疏数组 / 缓存结构（按 id 索引的数组、位标记等）这类
  实现细节可以单独标注。字段顺序尽量对齐代码里的声明顺序，便于对照。

### 6. 存储 / 表结构（ER / Redis）

- **布局**：ER 图或表格。表 / Redis key 用矩形（内部列字段），表间关系用连线 + 基数标注（`1:N` /
  `N:M`）。
- **风格**：首选 **Long Table**（表格感）；备选 **Monochrome**。
- **注意**：Redis 的 key 规则（前缀 / 拼接方式 / 过期时间）要写清，主键 / 外键标注，跨服共享的
  存储（按 account / 公会 id 共享的 MixRedis 之类）标清共享维度。

### 7. 状态机（代码视角）

- **布局**：节点 + 条件箭头。状态用圆 / 圆角矩形，迁移箭头标触发函数 / 事件 / 条件；初始态和终态
  用填充色区分。
- **风格**：首选 **Raw Grid**；备选 **Pin & Paper**、**Riptide Cobalt**。
- **注意**：迁移条件写成代码语义（事件名 / 函数名 / 布尔条件），不只标方向。终态 / 非法态要能一眼
  认出——用填充色或双层框（RULES 限制下不用多边形）。状态尽量和枚举值一一对应。

### 8. 算法 / 控制流

- **布局**：流程图。判断用单个菱形（RULES 允许一个简单菱形作 accent），循环、异常、回滚分支标清楚。
- **风格**：首选 **Raw Grid**；备选 **Lime Slab**。
- **注意**：判断条件写成布尔表达式（代码风格）。异常 / 失败分支（超时、断线、重试、回滚、幂等
  拦截）**不能省略**——只画 happy path 等于没画。循环标注退出条件。

## 三、策划 / 业务场景（次要）

这些场景重心不在代码，但团队偶尔也要画，按速查表选风格即可，注意点从简：

- **玩法流程**：阶段 pipeline，标阶段边界和失败分支（超时 / 断线 / 失败重试）。
- **数值 / 成长体系**：表格对齐，成长曲线用折线 `polyline`，不画自由曲线。
- **经济循环**：成环（产出 → 消耗 → 回收），箭头标「谁产出 / 谁消耗 / 多少」。
- **活动玩法图解**：先判断受众——玩家向用 Bold 活泼风，内部说明用克制风；奖励链路标达成条件与限购 / 去重。
- **版本 / 赛季时间线**：节点标起止时间窗，里程碑和日常迭代用颜色区分。

## 四、技术 / 代码通用注意事项

1. **标识符不翻译**：模块名、类名、字段名、类型、tag 号、Redis key（`GameServer`、`PlayerIDType`、
   `int32`、`CS/SC`）保留原样，中文只做注释——图里的名字必须能和代码 / 配置 / SDP 对上。
2. **方向语义是信息**：`CS` / `SC` / `Push` / `Forward` 的箭头方向承载语义，画反就是传达错误结论。
3. **类图 / 关系图绕开 polygon 限制**：继承三角、组合菱形画不出来，一律「箭头 + 文字」表达关系。
4. **分层习惯**：架构按「接口 / 逻辑 / 数据」或「接入 / 逻辑 / 存储 / 跨服」分层，别乱堆。
5. **状态机带条件、算法带失败分支**：迁移线标触发条件，控制流不省略异常路径。
6. **技术图克制**：代码 / 架构 / 协议 / 状态机 / 存储走 Restrained / Balanced 里的结构化风格
   （Raw Grid、Monochrome、Long Table、Riso Brut、Lime Slab），糖果色只留给玩家向宣传物料。
7. **遵守 RULES.md 硬规则**：只用原生图形（矩形 / 圆 / 折线 / 文字）、不用透明度和渐变、箭头用
   `marker-end`、不把用户指令 / 来源 / 风格名画上画板。

## 五、快速决策流

1. **定场景**：技术代码类对号第一节「技术 / 代码场景」，业务类对号「策划 / 业务场景」。
2. **定受众**：给程序 / 运维 → 结构化清晰（Raw Grid / Monochrome）；给策划 / 运营 → 可读 + 流程；
   给玩家宣传 → 活泼吸睛。
3. **选风格**：按速查表挑首选 / 备选，读对应 `templates/<slug>/design.md`，不要同时开多个模板对比。
4. **画图**：布局遵守本指南第四节 + RULES.md，渲染后自我检查（溢出 / 留白 / 重叠 / 手绘箭头）。
