# 端到端验收教学示例（完全脱敏）

> 本文是方法演示：人物、流程、编号全部为虚构抽象，不指向任何真实项目。
> 演示的功能："邀请码召回活动"——活跃玩家 A 生成邀请码并分享，流失回归玩家 B 输入邀请码领奖，A 累计召回人数完成任务。

## 演示一：玩家旅程时间线怎么走

**错误示范**：只验证"B 输入有效码 → 发奖成功"这一条路，就宣布功能没问题。

**正确示范**：从登录开始，两个真实玩家画像走完全程，每步问"玩家看到什么、该看到什么"：

1. **A 登录**：资格判定——A 是活跃玩家，不置回归位。此时 A 没有任何缓存数据，确认不会误建。
2. **A 打开活动界面**：拉状态——任务列表、召回人数(0)、邀请码(空)。玩家看到"邀请按钮可点"。
3. **A 点邀请按钮**：异步生成码——等待期玩家看到什么（转圈？按钮置灰？）；成功后应答带码 + 状态推送带码，**两条路都要有码**，否则玩家复制了码、界面却还显示空。
4. **时序异常插入**：如果 B 在活动**开始前**就登录过，资格判定当时不成立；活动开始后 B 不重登直接开界面——B 还能输码吗？（本例的正确答案：输码时现场补判定。如果没这个补救，就是一条 P0：玩家明明符合资格却被拒。）
5. **B 登录、开界面、输码**：每个拒绝分支 B 看到什么 toast；成功时弹奖励窗；A 侧此时收到计数推送，任务进度 +1。
6. **A 领奖**：任务完成后领奖入口出现、领完状态翻转为已领、界面刷新。
7. **活动结束**：玩家停在界面上继续操作，收到"活动已结束"的拦截反馈，而不是无反应。

## 演示二：一条 P1 是怎么被揪出来的

场景：服务端新增 6 个拒绝错误码，覆盖了"未绑定账号""无资格""码无效"等场景。

- 只看服务端：每个分支都回了错误包，逻辑闭环，看似没问题。
- 切换到玩家视角：玩家收到错误包 → 客户端按错误码查文案表 → **新错误码在文案表里不存在** → 弹空白 / 通用报错 → 玩家不知道自己该"先去绑定账号"，只会反复点、当 bug 上报。
- 结论：P1（回包正确但反馈无效），列入"需客户端确认"。

**教训：回包存在 ≠ 反馈有效。错误码的体验审计必须包含"客户端有没有这个码的文案"。**

## 演示三：对抗场景卡怎么打出真问题

卡【数据极端·重复数据】：同一玩家既是 A 的好友又是 A 的公会成员，推荐列表里出现几次？

- 实现从相似旧功能复制了"去重"逻辑：只出现在一个页签。
- 需求文档原文："两个页签下都会显示。"
- 结论：实现与文档冲突，以文档为准，删去重。

**教训：从参考功能复制来的逻辑，要逐条对照新需求文档；冲突时以新文档为准。"旧功能一直这么跑"不是理由。**

## 演示四：什么算"已验证"，什么算"需确认"

| 陈述 | 归类 |
|---|---|
| 每个拒绝分支都回了错误应答（读了全部提前返回点） | ✅已验证 |
| 去重检查在发奖之前（读了两行的行号先后） | ✅已验证 |
| 客户端会把奖励列表渲染成弹窗 | ⚠️需客户端确认 |
| 新错误码有玩家文案 | ⚠️需客户端确认（大概率没有，列为 P1） |
| 空入参的批量查询一定会触发回调 | ⚠️需确认（框架未保证时，代码里必须显式短路兜底） |
| 玩家离线时转发失败，计数丢失 | 已知边界（与线上同类功能一致，注明先例，不冒充无问题） |
